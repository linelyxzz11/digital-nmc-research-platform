# 输入加载 RTL 诊断与对照实验

本轮覆盖两个已有 GEMV 形状、两种映射，共四个用例。每个用例运行五种加载配置，共 20 次。全部输入 SRAM 读回、包数量和事件身份检查通过，四个原配置精确复现历史输入周期。发布前再次从 main 基点重跑，20 项输入周期与初次诊断完全一致。

## 结果

下表均为输入加载周期。

| GEMV / 映射 | 1 B 写口，1 包在途 | 1 B，4 包 | 1 B，8 包 | 4 B，1 包 | 4 B，8 包 |
|---|---:|---:|---:|---:|---:|
| 161×97 / unindp-compact | 2313 | 595 | 311 | 2013 | 275 |
| 161×97 / noc-v04 | 2021 | 519 | 277 | 1721 | 241 |
| 251×127 / unindp-compact | 2969 | 759 | 395 | 2585 | 347 |
| 251×127 / noc-v04 | 2593 | 663 | 353 | 2209 | 305 |

**单独拓宽写口使加载周期减少约 13%–15%。保留 1 B 写口并允许 8 个请求在途，使加载周期减少约 86%。** Host 可以让不同包的网络传输、SRAM 写入和 ACK 返回重叠。

161×97 分发 388 个有效输入字节、100 个包。251×127 分发 508 字节、128 个包。两种映射各有四个行分组，输入复制到这些分组。原配置下，数据去程与 ACK 回程合计约占基线加载时间的 61%。

| 原基线阶段 | 161×97 | 251×127 |
|---|---:|---:|
| Host 入队至 Tile 收齐包，含 NI 和网络 | 756 | 972 |
| 收齐包至 SRAM 接受请求 | 100 | 128 |
| SRAM 接受请求至本地响应接受 | 500 | 640 |
| 本地响应至 ACK 入队 | 100 | 128 |
| ACK 入队至 Host 接受 | 656 | 844 |
| Host 间隔与阶段边界余量 | 201 | 257 |
| 合计 | 2313 | 2969 |

每个事件记录在时钟采样边沿。串行配置的各请求无重叠，可将这些间隔相加。窗口配置中存在重叠，逐请求延迟之和不能用作总周期。Host 间隔与边界余量由完整加载周期减去上述事件间隔总和得到。

## 实验范围

- 使用现有 64 Tile Mesh RTL 和四个历史 plan，固定 seed=20261031，保留输入字节和地址。
- 脚本在输出目录生成观测 testbench 和 4 B 写口 SRAM 变体。窗口控制位于 Host testbench 驱动器，允许最多 1/4/8 个已发送且尚未 ACK 的请求。
- 每次运行都从真实 Input SRAM 端口读回所有被加载的字节，并验证 send/tail/request/response/ACK 事件的数量及节点和序号身份。
- 计时从原 load_start 开始，到原 task_valid 启动边界结束，包含同样的一个边界周期。
- 为单独测量加载，权重初始化被省去，MAC 尚未启动即结束实验。优化后的完整 GEMV 周期、映射排名与 NMC/集中计算加速比仍需完整回归。
- 4 B 并行写为实验 SRAM 组织假设，需要后续实现和资源评估。多请求窗口还需要实际 Host 控制器实现与验证。本次证据针对输入加载。

## 复现

在仓库根目录安装原项目 Python 依赖，并确保 PATH 中有 iverilog、vvp。

```bash
python -B tools/experiments/input_loading_audit.py --output-dir dump/input_loading_audit_recheck
```

使用新的输出目录。完整 20 项输入诊断在本次机器上约需 80 秒，具体时间记录在 provenance.json。

- results.json 保存周期、数据量、检查状态及串行阶段分解。
- summary.csv 保存五种配置的周期、减少比例与有效 B/周期吞吐。
- stage_cycles.csv 保存串行配置的阶段分解。
- input_traces.tar.gz 保存全部 20 项事件 CSV、仿真日志、输入包和计划。
- provenance.json 保存基点 commit、脚本/RTL/证据 SHA256、工具版本和运行时间。
